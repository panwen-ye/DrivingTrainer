# 技术与服务架构

## 1. 总体方案

采用 Apple 原生、本地优先架构：Swift + SwiftUI，iPhone 为数据权威端，Watch 为轻量伴随端。两周 MVP 不建设独立后端，也不引入第三方包。

```text
Apple Watch App
  快捷控制 / 震动 / 状态
          │ WatchConnectivity
          ▼
iPhone App
  SwiftUI 界面
  ├── 训练会话协调
  ├── 路线与节点管理
  ├── Core Location 定位
  ├── MapKit 地图
  ├── AVSpeechSynthesizer 语音
  └── Codable + JSON 文件存储
          │
          ├── 本地图片与导出文件
          └── CloudKit（第二阶段可选）
```

## 2. 分层职责

| 层 | 职责 | 依赖原则 |
|---|---|---|
| App/UI | 页面、导航、权限引导、状态展示 | 可依赖 Feature 与 Domain |
| Feature | 录制、节点编辑、训练、报告 | 依赖 Domain 抽象协议 |
| Domain | 实体、规则、用例、提醒判定 | 不依赖 UI 和系统框架 |
| Infrastructure | 定位、JSON 持久化、语音、Watch 通信 | 实现 Domain 协议 |
| Service | 未来云同步、AI 分析 | MVP 不成为核心路径 |

## 3. Apple 能力选择

- UI：SwiftUI。
- 地图：MapKit；首版不依赖第三方地图 SDK。
- 定位：Core Location，路线录制时申请“使用 App 期间”，确有后台录制需求时再引导“始终允许”。
- 数据：MVP 使用 Codable + 原子化 JSON 文件；结构化查询增加后再迁移 SwiftData。
- 语音：系统语音合成；避免首版依赖联网语音服务。
- Watch 通信：WatchConnectivity；MVP 只传下一节点摘要和提醒事件。
- 后台：优先完成前台稳定录制；若真机验证顺利再启用 Location updates，不阻塞首个可安装版本。
- 可选同步：CloudKit，等本地版本稳定后加入。

## 4. 运行时关键流程

### 路线录制

`开始录制 → 获取权限 → 采样位置 → 过滤异常点 → 持久化 TrackPoint → 快速标记节点 → 结束并生成摘要`

### 节点提醒

`位置更新 → 匹配当前路线进度 → 计算到下一节点距离 → 进入提醒半径 → 去重/冷却 → 手机语音 + Watch 震动`

### Watch 操作

`手机进入提醒范围 → 向手表发送节点摘要 → 手表震动并展示一句口诀`

## 5. 数据与隐私

- GPS、照片和训练记录默认只存本机。
- 未开启云同步时不上传任何位置数据。
- 导出时由用户主动选择范围和接收位置。
- 日志不得记录完整连续坐标；诊断导出需做显式提示。
- 路线底图及照片必须确认授权，不把当前 HTML 中的本机图片路径直接带入 App。

## 6. 后端预留

未来只有出现以下需求时才引入服务端：跨账号共享、公开路线审核、非 Apple 平台同步或服务端 AI。个人版优先使用 CloudKit，降低部署和运维成本。

若后续必须自建，边界建议为：认证、路线版本、媒体签名上传、同步冲突和分析任务；iPhone 本地功能不能因服务不可用而失效。

## 7. 轻量化预算

- 第三方运行时依赖：0。
- 网络请求：核心流程 0 次。
- 后台常驻：仅主动训练时定位；结束后立即停止。
- 图片资源：MVP 不打包路线照片，App 图标之外尽量使用 SF Symbols。
- 架构模块：保留清晰边界，但不提前拆成多个仓库或微服务。
